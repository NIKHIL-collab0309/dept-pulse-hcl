# Department-wise Performance Analysis

A Streamlit prototype for analysing academic performance across the **B.Tech, MCA, BCA and MBA** programmes of an assumed college context (**ABES**).

> **Synthetic data only.** Every figure comes from dataset `SYNTH-DPA-1.0` (seed `42`), generated by `src/generate_data.py`. No real student, staff or institutional records are used.

---

## 1. Quick start (local)

```bash
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python src/generate_data.py          # builds data/app.db (skip if it already exists)
streamlit run app.py
```

**Live demo:** https://dept-pulse-live.streamlit.app

Run the tests:

```bash
python -m pytest -q
```

Requires Python 3.12 or newer (it uses `tomllib` from the standard library).

**How credentials are loaded (NFR-05 / NFR-07)**

- No password, and no hash, is written in any Python file.
- The app reads `st.secrets["users"]`. To use your own credentials, copy `.streamlit/secrets.toml.example` to `.streamlit/secrets.toml` and edit it. `secrets.toml` is git-ignored.
- If no `secrets.toml` exists (a fresh clone, or the test suite), the app falls back to reading the `[users]` table from `.streamlit/secrets.toml.example`, so the demo works out of the box.
- The **Prototype Demo Accounts** helper on the login screen reads the `[demo_accounts]` table from that same example file. **Change every password and delete `[demo_accounts]` before any shared deployment.**

To create a new hash:

```bash
python -c "import hashlib; print(hashlib.sha256('NewPassword'.encode()).hexdigest())"
```

## 3. Role-based access

| | Dean of Academics | Department HOD |
|---|---|---|
| Data scope | All 4 programmes, or any single programme | Bound programme only |
| SQL | `WHERE programme_code IN (?,?,?,?)` or `= ?` | Always `WHERE programme_code = ?` with the bound code |
| Programme filter | Selectbox: *All Programmes*, B.Tech, MCA, BCA, MBA | Locked, read-only field |
| Page 02 | **Programme Comparison** (cross-programme) | **Course & Category Comparison (My Department)**: Core, Elective, Practical and Project within the department |
| KPI-06 grouping | Programme | Course or category |

**Login binding.** HODs pick their department at sign-in. If it doesn't match the `programme_code` bound to the username in secrets, the login is rejected with a "Department mismatch" error. Choosing the wrong role is also rejected.

**Isolation is enforced in layers.**

1. The scope comes from the authenticated user, never from a widget (`filters.resolve_programme_scope`).
2. The loader validates programme codes and binds them as parameters (`data_loader`).
3. Every DataFrame is re-checked before it reaches a page. Any row from outside the user's scope raises `ScopeViolationError` (`filters.enforce_scope`).
4. The session record is re-validated on every run. A tampered session (for example, an HOD claiming `ALL`) is treated as logged out.
5. While signed out, every analytical URL resolves to the sign-in screen, so deep links never run an analytical script.

**Session.** The sidebar and every page header show a role and scope badge, for example `Role: HOD — MCA | Scope: Restricted to MCA`. **Logout** clears `st.session_state` completely and calls `st.rerun()`.

## 4. Data and business rules

`data/app.db` (SQLite) is created by `src/generate_data.py`. Its schema is in `sql/schema.sql`, extracted verbatim from the generator's `DDL_SCRIPT`. The app opens the database **read-only**, with `PRAGMA foreign_keys = ON`, at a path resolved from the repository root.

| Object | Rows |
|---|---|
| `programme_master` | 4 |
| `academic_period_master` | 4 (2025-26 Sem 1 → 2026-27 Sem 2) |
| `course_master` | 48 (12 per programme) |
| `performance_fact` | 195 |
| `data_quality_issue` | 24 |
| `vw_department_performance_analysis` | 39-column view |

**Cleaning (`src/cleaning.py`)**

- `performance_id` 193, 194 and 195 repeat the `(programme_id, period_id, course_id)` grain of rows 15, 62 and 118.
- **Cleaned** mode keeps the lowest `performance_id` per grain, giving 192 rows. **Raw** mode keeps all 195.
- Switch between them with the sidebar **Dataset Mode** toggle. Page 06 compares the KPIs under both modes.
- NULLs are never coerced to 0. Each one is excluded only from the denominator of the metric it affects. A slice with no project or practical records shows **"Not available"**.

**Weighted KPIs (`src/analytics.py`)**

These are always ratios of sums, never unweighted means of percentage columns.

| ID | KPI | Formula |
|---|---|---|
| KPI-01 | Overall Attendance % | `SUM(present) / SUM(eligible) × 100` |
| KPI-02 | Average Assessment % | `SUM((marks / max) × 100 × assessed) / SUM(assessed)`, non-NULL marks only. Split by type: Internal /50, End-Semester /100, Practical /50 |
| KPI-03 | Pass % | `SUM(passed) / SUM(appeared) × 100` |
| KPI-04 | Project Completion % | `SUM(completed) / SUM(assigned) × 100`, where assigned > 0 and completed is not NULL |
| KPI-05 | Practical Average % | `SUM((score / max) × 100 × assessed) / SUM(assessed)`, non-NULL scores only |
| KPI-06 | Highest / lowest | By programme (Dean) or course/category (HOD). Ties are all returned |
| KPI-07 | Period change | `current_rate − prior_rate` in **percentage points (pp)**, ordered by `period_sequence` 1 → 4 |

`SUM(enrolled_count)` is labelled **Total Course-Seat Enrolments**. It is not a unique student headcount.

**Statistics (`src/statistics.py`):** count, mean, median, min, max, sample standard deviation (`ddof=1`), Q1, Q3, IQR, Tukey fences (`Q1 − 1.5×IQR`, `Q3 + 1.5×IQR`), skewness, pairwise Pearson correlation, and an OLS trendline (statsmodels).

## 5. Pages

| Page | Content |
|---|---|
| 01 Overview | KPI cards with pp delta badges, programme/course summary, KPI bar and trend charts, scoped CSV download |
| 02 Programme Comparison / Course & Category Comparison | Highest/lowest callouts (KPI-06), full KPI table, grouped bars, per-period trend and pp movements |
| 03 Attendance Analysis | Numerator/denominator breakdown, trend for periods 1–4, present vs absent sessions, category comparison, low-attendance watchlist |
| 04 Results Analysis | Pass % trend with pp change, appeared vs passed, assessment-type comparison, attendance-vs-marks scatter with OLS trendline |
| 05 Project & Practical Analysis | KPI-04/05, coverage counts, "Not available in this dataset" where no records exist |
| 06 Data Quality | Issue log (by code, severity and status), live validation checks, duplicate pairs, live IQR scan, raw vs cleaned KPI table |
| 07 Statistics & EDA | Metric selector, descriptive statistics, box/violin plot and histogram with fences, correlation heatmap |

The decorative banner, scope badge, synthetic-data notice and KPI cards are rendered with `st.iframe`, using the Tailwind CSS CDN plus inline CSS as a fallback. All dynamic text is passed through `html.escape`. Filters, tables, downloads and Plotly charts are native Streamlit components.

## 7. Deploy to Streamlit Community Cloud

1. Generate the database locally (`python src/generate_data.py`) and commit `data/app.db`. The app opens it read-only and never regenerates it at runtime.
2. Push the repository to GitHub. Make sure `.streamlit/secrets.toml` is **not** committed; `.gitignore` covers this.
3. On share.streamlit.io, choose **Create app**, then select the repo and branch, with main file `app.py`.
4. Under **Advanced settings**, choose Python **3.12**.
5. In **Secrets**, paste a `[users]` section in the same format as `.streamlit/secrets.toml.example`, with new password hashes. Don't paste `[demo_accounts]` unless the deployment is for reviewers only.
6. Deploy. The dark theme is applied from `.streamlit/config.toml`.

If no secrets are configured, the deployed app falls back to the demo hashes in `secrets.toml.example`. That is acceptable for an academic demo, but not for anything shared more widely.
